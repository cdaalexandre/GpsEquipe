POWERSHELL 5.1
- `curl` é alias de Invoke-WebRequest: os testes da Seção 14 da v1 não colam.
  Usar Invoke-RestMethod ou curl.exe.
- `;` separa comandos; `&&` não existe.
- Nunca criar arquivo com `>` (gera UTF-16). Set-Content gera BOM; para
  .cs/.json/.html sem BOM:
  [IO.File]::WriteAllText($caminho, $texto, [Text.UTF8Encoding]::new($false))
- Write-Output sai na hora; objeto formatado (Format-Table) sai no fim do
  pipeline. Saída fora de ordem é flush, não erro. Usar | Out-String quando a
  ordem importa.
- `--query "length(items)"` perde as aspas e o az recebe os parênteses soltos.
  Contar em PowerShell: @($obj.items).Count
- Crases dentro de --query não sobrevivem. Filtrar em PowerShell, não no JMESPath.
- Nunca usar o clipboard para passar valor entre passos: colar o output no chat
  sobrescreve o clipboard. Valor sensível vai de comando → variável → arquivo,
  dentro do MESMO bloco.
- Confirmação de escrita precisa checar $LASTEXITCODE. "Write-Output OK" fixo
  mente quando o comando anterior falha.
- Nunca suprimir stderr (2>$null) em comando de ESCRITA: esconde a causa da falha.
 
AZURE CLI
- `az functionapp list-runtimes --os linux` devolve ARRAY na raiz, não objeto
  com chave .linux. Filtrar com @($r) | Where-Object { $_.runtime -eq '...' }.
- `--os linux` refere-se ao SO do plano NO AZURE, não à máquina de
  desenvolvimento. Compila-se no Windows e publica-se em host Linux.
- JMESPath é CASE-SENSITIVE. !contains(name,'STORAGE') NÃO pega
  'AzureWebJobsStorage'. Foi o que causou o incidente de segredo (Seção 8).
- `az functionapp config set --linux-fx-version` falhou com exit 255 sem alterar
  o valor. Quem atualiza é o `func publish`, que lê o TargetFramework do .csproj.
- `az functionapp keys list --query masterKey` dá a chave para o admin API;
  `az functionapp function keys list --function-name X --query default` dá a
  chave DE FUNÇÃO, específica e revogável sozinha.
- `func azure functionapp logstream` NÃO existe em Linux Consumption.
- `az monitor app-insights query --app` espera o NOME do componente quando
  usado com --resource-group, não o appId (GUID).
- `az storage entity insert` INFERE o tipo. Um celular só com dígitos vira
  Int32 e estoura: "5511000000000 is too large to be cast to EdmType.INT32".
  Sufixos como Campo=valor:str NÃO são interpretados — ficam dentro do dado.
  Para garantir string, use um valor com caractere não numérico.
- `az storage entity delete` exige --partition-key E --row-key: não existe
  exclusão acidental em massa nesse comando.

    curta. Se a API Key vazar, a única correção é regenerar e redistribuir —
    foi exatamente o que aconteceu com a account key nesta mesma sessão.
 
INCREMENTO 4 — LGPD: ANONIMIZAÇÃO (2026-09-13, commit 5defb47)
  Timer trigger AnonimizarCoordenadas, CRON "0 30 3 * * *" (3h30 UTC, 00h30 BRT).
  Pacote Microsoft.Azure.Functions.Worker.Extensions.Timer 4.3.1.
  Retenção: 90 dias. Filtro "PartitionKey lt 'yyyy-MM-dd'" — comparação
  lexicográfica, que funciona porque o formato é ordenável como texto.
  Valor final: "ANONIMIZADO" literal, SEM hash. Hash de celular é quebrável por
  força bruta em minutos, o que seria pseudonimização disfarçada.
  Idempotente: pula quem já está anonimizado.
  CONCEITO PARA O RELATÓRIO — anonimização × pseudonimização:
    Anonimização remove o vínculo com a pessoa de forma irreversível.
    Pseudonimização troca o dado por um código e guarda a correspondência em
    outro lugar — é reversível, e por isso continua sendo dado pessoal sob a LGPD.
  CONCEITO — Timer trigger × HTTP trigger:
    Timer é disparado pelo relógio, sem cliente e sem resposta: só efeito
    colateral e log. HTTP espera um cliente e devolve resposta.

REGRAS DE FORMATO DO PIN (validadas no servidor, em DefinirPin):
  exatamente 6 dígitos; recusa PIN com todos os dígitos iguais; celular precisa

TRABALHO FUTURO DECLARADO (não escondido):
  - PBKDF2 roda a cada envio, ou seja a cada 10s por colaborador (~50-100ms de
    CPU por coordenada). O correto é conferir o PIN uma vez e emitir token de
    sessão curto. Arquiteturalmente errado, funcionalmente irrelevante no
    Consumption.
  - Sem bloqueio por tentativas erradas: 6 dígitos = 1 milhão de combinações e o
    endpoint é anônimo. O PBKDF2 encarece a tentativa, não a impede.
  - PIN é fator único e fraco: elevou o sistema de "sem autenticação nenhuma"
    para "autenticação fraca", não para "forte".
  - Quilometragem e custo em R$ (cogitado como Incremento 5) movido para
    trabalho futuro: o dado de quilometragem da DECO não está disponível neste
    semestre.

LIÇÕES DESTA MÁQUINA (complementam a Seção 7):
  - Read-Host -AsSecureString dentro de bloco & { } colado no console NÃO
    captura entrada no PS 5.1: devolve string vazia, e o erro aparece só do
    lado do servidor como 400. Gerar o valor, não digitar.
  - RandomNumberGenerator.GetInt32 é .NET Core 3.0+. O PS 5.1 roda sobre .NET
    Framework 4.x: usar RNGCryptoServiceProvider.GetBytes. Mesmo padrão do 503:
    API que existe no .NET moderno e não existe no host que executa.
  - Laço do/until sem teto de tentativas realimenta o erro dezenas de vezes.
  - Ler corpo de erro HTTP no PS 5.1 exige StreamReader sobre
    $_.Exception.Response.GetResponseStream(). $_.ErrorDetails.Message vem vazio.
  - func publish com 2>&1 gera NativeCommandError falso: o func escreve
    progresso em stderr. Não usar 2>&1 com func.
  - Conta sem papel RBAC de dados no Storage (Storage Table Data Reader ausente):
    usar --auth-mode key, não --auth-mode login.
  - Teste que dependa do clipboard é incompatível com colar output no chat: o
    próprio ato de copiar o output destrói o valor guardado.
  - Bloco muito longo colado neste console pode corromper linha (duplicação e
    quebra observadas). Para texto grande, gravar arquivo e mover, não colar.
