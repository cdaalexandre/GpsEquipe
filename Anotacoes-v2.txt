POWERSHELL 5.1
- `curl` é alias de Invoke-WebRequest: os testes da Seção 14 da v1 não colam.
  Usar Invoke-RestMethod ou curl.exe.
- `;` separa comandos; `&&` não existe.
- Nunca criar arquivo com `>` (gera UTF-16). Set-Content gera BOM; para
  .cs/.json/.html sem BOM:
  [IO.File]::WriteAllText($caminho, $texto, [Text.UTF8Encoding]::new($false))
- Write-Output sai na hora; objeto formatado (Format-Table) sai no fim do
  pipeline. Saída fora de ordem é flush, não erro. Usar | Out-String quando a
  ordem importa.
- `--query "length(items)"` perde as aspas e o az recebe os parênteses soltos.
  Contar em PowerShell: @($obj.items).Count
- Crases dentro de --query não sobrevivem. Filtrar em PowerShell, não no JMESPath.
- Nunca usar o clipboard para passar valor entre passos: colar o output no chat
  sobrescreve o clipboard. Valor sensível vai de comando → variável → arquivo,
  dentro do MESMO bloco.
- Confirmação de escrita precisa checar $LASTEXITCODE. "Write-Output OK" fixo
  mente quando o comando anterior falha.
- Nunca suprimir stderr (2>$null) em comando de ESCRITA: esconde a causa da falha.
 
AZURE CLI
- `az functionapp list-runtimes --os linux` devolve ARRAY na raiz, não objeto
  com chave .linux. Filtrar com @($r) | Where-Object { $_.runtime -eq '...' }.
- `--os linux` refere-se ao SO do plano NO AZURE, não à máquina de
  desenvolvimento. Compila-se no Windows e publica-se em host Linux.
- JMESPath é CASE-SENSITIVE. !contains(name,'STORAGE') NÃO pega
  'AzureWebJobsStorage'. Foi o que causou o incidente de segredo (Seção 8).
- `az functionapp config set --linux-fx-version` falhou com exit 255 sem alterar
  o valor. Quem atualiza é o `func publish`, que lê o TargetFramework do .csproj.
- `az functionapp keys list --query masterKey` dá a chave para o admin API;
  `az functionapp function keys list --function-name X --query default` dá a
  chave DE FUNÇÃO, específica e revogável sozinha.
- `func azure functionapp logstream` NÃO existe em Linux Consumption.
- `az monitor app-insights query --app` espera o NOME do componente quando
  usado com --resource-group, não o appId (GUID).
- `az storage entity insert` INFERE o tipo. Um celular só com dígitos vira
  Int32 e estoura: "5511000000000 is too large to be cast to EdmType.INT32".
  Sufixos como Campo=valor:str NÃO são interpretados — ficam dentro do dado.
  Para garantir string, use um valor com caractere não numérico.
- `az storage entity delete` exige --partition-key E --row-key: não existe
  exclusão acidental em massa nesse comando.

    foi exatamente o que aconteceu com a account key nesta mesma sessão.

  B — LIÇÕES DESTA MÁQUINA (complementa a Seção 7)
--------------------------------------------------------------------------------
1. CORPO DE ERRO NO POWERSHELL 5.1 — a lição anterior estava incompleta, e a
   causa agora está medida. O Invoke-WebRequest lê e CONSOME o stream de erro
   para popular $_.ErrorDetails.Message SOMENTE quando a resposta de erro é
   JSON. Medido no mesmo bloco, em 15/09/2026:
     400 com application/json; charset=utf-8
       -> ErrorDetails.Message PREENCHIDO, StreamReader VAZIO
     403 com text/plain; charset=utf-8
       -> ErrorDetails.Message VAZIO, StreamReader com o texto
   REGRA ROBUSTA, aplicada em demo/Demo-2-Preparar.ps1 e no cena.ps1 gerado por
   ele: tentar ErrorDetails.Message primeiro e cair no StreamReader apenas se
   vier vazio. Nunca depender de um dos dois isoladamente.
   CONSEQUÊNCIA QUE QUASE PASSOU: o aceite automático da cena 4 comparava só se
   os três textos eram iguais. Três textos VAZIOS também são iguais, então o
   script marcaria PRONTO e o vídeo gravaria um 403 sem mensagem na tela. O
   aceite passou a exigir corpo legível nos três casos.

2. CORS CONFERIDO COMO O NAVEGADOR CONFERE — dá para simular o preflight sem
   abrir navegador, mandando OPTIONS com os headers Origin,
   Access-Control-Request-Method e Access-Control-Request-Headers.
   Resultado em 15/09/2026, nas três rotas administrativas:
     HTTP 204, allow-origin igual à origem do site estático,
     allow-headers content-type, allow-methods POST.
   Com Origin de um domínio estranho: HTTP 204 SEM allow-origin, e é isso que
   faz o navegador abortar a chamada. A permissão é dirigida, não curinga —
   decisão tomada na Fase 1 e só comprovada agora.

3. ARQUIVO GRAVADO COM LF E O AVISO DO GIT — todo arquivo criado por
   [IO.File]::WriteAllText sai com LF, e o git avisa que vai trocar por CRLF na
   próxima vez que tocar o arquivo. Efeito prático: âncora de várias linhas
   para edição por Replace() quebra depois de um checkout. Editar sempre por
   âncora de UMA linha.

4. BLOB ATUALIZADO NÃO APARECE SEM RECARGA FORÇADA — depois de um upload com
   --overwrite, o navegador continua servindo a versão em cache. Conferir
   sempre pelo tamanho em bytes e recarregar com Ctrl+F5.

5. TESTE DE ACENTO QUE NÃO TESTA NADA — a verificação de integridade do

Em PowerShell 5.1, @(a,b,c) | Where-Object { ... } devolve ESCALAR quando sobra
um unico item: o @() envolve o ARRAY DE ENTRADA, nao a saida do pipeline. Para
garantir array, o @() precisa envolver o pipeline inteiro: @( ... | Where ... ).

Efeito observado: $cand era string e $cand[0] devolveu o primeiro CARACTERE
dela, o "C" de "C:\Users\...". O erro apareceu tres blocos adiante, na forma de
"nao e possivel chamar um metodo em uma expressao de valor nulo", longe da
causa real.

Dano evitado: a cadeia de nulos fez o WriteAllText gravar o Anotacoes-v2.txt
com ZERO bytes. O arquivo foi restaurado automaticamente porque o script tinha
feito backup antes e validava o resultado depois (presenca do trecho, presenca
de cedilha e til, ausencia de caractere de substituicao U+FFFD).

Regra adotada: script que sobrescreve arquivo com historico faz backup antes,
valida depois e restaura sozinho se a validacao falhar. Validacao pos-escrita
vale mais que confianca na logica de escrita.
