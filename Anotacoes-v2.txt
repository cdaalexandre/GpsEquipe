  SEÇÃO 7 — LIÇÕES DESTA MÁQUINA (para não reaprender)
────────────────────────────────────────────────────────────────────────────────
- Ferramenta instalada só aparece em janela de PowerShell aberta DEPOIS da
  instalação. Fechar e reabrir a mesma janela não basta se o install rodou nela.
- winget funciona com admin local nesta máquina; não precisou de chamado à TI.
- `curl` no PowerShell 5.1 é alias de Invoke-WebRequest: os testes da Seção 14
  da v1 não colam. Usar Invoke-RestMethod ou curl.exe.
- `;` separa comandos; `&&` não existe no PowerShell 5.1.
- Nunca criar arquivo com `>` (gera UTF-16). Set-Content gera BOM; para .cs/.json/.html
  sem BOM: [IO.File]::WriteAllText($caminho, $texto, [Text.UTF8Encoding]::new($false))
- Execution policy travada por GPO: só -Scope Process ou Unblock-File.
- Repositório fora do OneDrive (C:\repo) por causa de bin/ e obj/.
- Write-Output sai na hora; objeto formatado (Format-Table) sai no fim do
  pipeline. Saída fora de ordem é flush, não erro. Usar | Out-String quando a
  ordem importa.
- `az functionapp list-runtimes --os linux` devolve ARRAY na raiz, não objeto
  com chave .linux. Filtrar com @($r) | Where-Object { $_.runtime -eq '...' }.
- JMESPath é CASE-SENSITIVE. !contains(name,'STORAGE') NÃO pega
  'AzureWebJobsStorage'. Foi o que causou o incidente da Seção 8.
- Nunca usar o clipboard para passar valor entre passos: colar o output no chat
  sobrescreve o clipboard. Valor sensível vai de comando para variável para
  arquivo, dentro do MESMO bloco.
- Confirmação de escrita precisa checar $LASTEXITCODE. "Write-Output OK" fixo
  mente quando o comando anterior falha.
- A chave de storage da v1 vazou (estava nas anotações v1). Nada dela é
  reaproveitado. Se a v1 continuar viva, rotacionar:
  az storage account keys renew --account-name rastreiogpsstdbad1 --resource-group RastreioGPS-Std-RG --key key1
  e atualizar os app settings da Function App v1.

CAUSA RAIZ CONFIRMADA:
  .NET 10 é ANUNCIADO no catálogo do Linux Consumption (DOTNET-ISOLATED|10.0)
  mas NÃO está operante nesse plano. O worker nunca inicializa, e por isso não
  há telemetria nenhuma.
  Prova: trocando SOMENTE o TargetFramework de net10.0 para net9.0 — mesmo
  código, mesmo app, mesmo plano, mesma chave — o publish sincronizou os
  triggers e o host respondeu HTTP 200.

Procedimento do rebaixamento:
  1. TargetFramework para net9.0 no GpsEquipe.csproj
  2. Remove-Item .\obj, .\bin -Recurse -Force   (obrigatório ao trocar framework)
  3. dotnet build  → êxito
  4. func azure functionapp publish GpsEquipe-App-bad1
     → "Detected target framework: net9.0"
     → "Updating 'linuxFxVersion' to 'DOTNET-ISOLATED|9.0'."
     → Syncing triggers... com as duas Invoke urls listadas

DECISÃO: a v2 fica em net9.0. Migrar para Flex Consumption (onde o .NET 10 deve
estar operante) é trabalho futuro documentado. Observar que o .NET 9 é STS, não
LTS — o mesmo tipo de problema de fim de suporte que motivou a saída do
in-process reaparece aqui, agora na camada de hospedagem.

Lições de ferramenta descobertas neste diagnóstico:
  - `az functionapp config set --linux-fx-version` falhou com exit code 255 sem
    alterar o valor. Quem atualizou o linuxFxVersion foi o `func publish`, que
    lê o TargetFramework do .csproj.
  - `func azure functionapp logstream` NÃO existe em Linux Consumption:
    "Log stream is not currently supported in Linux Consumption and Flex Apps."
  - `az monitor app-insights query --app` espera o NOME do componente quando

  - Trocar de target framework exige apagar obj/ e bin/ antes do build.
